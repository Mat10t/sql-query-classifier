# Этап 1. Постановка задачи, целевая величина и протокол повторных измерений

## 1. Постановка задачи

Дано: SQL-запрос `q` (один `SELECT`) и фиксированное окружение `E`: схема, данные, индексы, статистика, конфигурация PostgreSQL, оборудование.

Требуется **до выполнения запроса** получить численную оценку его ресурсоёмкости

```
ĉ(q) = f(x_plan(q), x_sql(q))
```

где

- `x_plan(q)` - признаки плана из `EXPLAIN` (без `ANALYZE`): оценки оптимизатора, структура плана, типы операций, оценки строк и ширины;
- `x_sql(q)` - признаки SQL-текста (дополнительная группа, проверяется в ablation на этапе 6);
- параметры окружения `x_env` в 7 семестре не варьируются: окружение фиксировано и описано в снимке стенда (этап 3).

Отличие от прототипа 6 семестра: вместо бинарной метки light/heavy прогнозируется численная величина. Бинарная классификация сохраняется как baseline для дискретного сценария: метка `label = [t(q) > 75-й процентиль t]`.

## 2. Целевая величина

**t(q)** - фактическое время выполнения запроса на сервере, мс:

> медиана значения `Execution Time` из `EXPLAIN (ANALYZE, TIMING OFF, BUFFERS, FORMAT JSON)` по K = 5 измеренным запускам, выполненным после W = 1 прогревочного запуска, в одной сессии с фиксированными параметрами.

Пояснения к выбору:

| Решение | Обоснование |
|---|---|
| Время выполнения, а не Total Cost или число прочитанных блоков | понятно, связано с нагрузкой на SQL-сервис, используется как основная мера в работах по прогнозу производительности запросов (см. этап 2) |
| `Execution Time` из EXPLAIN ANALYZE | исключает передачу результата клиенту и сетевые задержки: измеряется работа сервера над запросом. Время планирования (`Planning Time`) сохраняется отдельно и в t(q) не входит |
| `TIMING OFF` | без него PostgreSQL замеряет время каждого узла плана, и на запросах с миллионами строк эти накладные расходы искажают общее время. Общий `Execution Time` с `TIMING OFF` сохраняется |
| Медиана, а не среднее | устойчива к единичным выбросам (фоновые процессы хоста: Windows, WSL2, Docker), поэтому отдельные запуски не отбрасываются |
| "Тёплый" режим (после прогрева) | холодный кэш на Docker/WSL2 нельзя надёжно сбросить без перезапуска сервера и ОС; тёплый режим воспроизводим и соответствует повторяющимся запросам в работающем сервисе |

Фактические метрики выполнения используются **только** как целевая величина и для контроля качества измерений. В признаки они не входят: см. этап 3 и `src/checks/check_leakage.py`.

## 3. Протокол повторных измерений

Реализация: `src/measure/protocol.py`, сбор - `src/db/collect_dataset.py`.

| Параметр | Значение |
|---|---|
| Прогревочные запуски W | 1 (результат не используется) |
| Измеренные запуски K | 5 |
| Агрегирование | медиана - `execution_time_ms`; также сохраняются min, max, mean, std, CV |
| Выбросы | не отбрасываются: медиана устойчива к ним. Запрос с CV > 0.2 помечается `is_unstable = 1` для анализа |
| Таймаут | `statement_timeout = 120 s`; при превышении `status = timeout`, t(q) не определяется, запрос не попадает в обучение |
| Параметры сессии | `jit = off`, `max_parallel_workers_per_gather = 0` |
| Порядок | запросы выполняются последовательно в одной сессии, без параллельной нагрузки |
| Сохранение | все запуски (включая прогревочные) - `data/processed/measurements.csv` |

## 4. Эксперимент с повторами: обоснование W и K

Из каждого из 31 шаблона берётся один запрос, который выполняется 15 раз подряд без прогрева. Запуск 0 считается "первым запуском". Запуски 1-7 - блок оценки, запуски 8-14 - независимый эталонный блок. Для k = 1...7 медиана первых k запусков блока оценки сравнивается с медианой эталонного блока: с прогревом (запуск 0 отброшен) и без него (запуск 0 входит в оценку).

Запуск: см. README, раздел "Полное воспроизведение". Анализ - `python -m src.analysis.repeatability`. Результаты: [reports/stage1](../reports/stage1).

### Результаты (31 запрос x 15 запусков)

Сходимость медианы первых k запусков к эталонной медиане (относительная ошибка; [repeatability_convergence.csv](../reports/stage1/repeatability_convergence.csv), [график](../reports/stage1/repeatability_convergence.png)):

| k | Медиана ошибки, с прогревом | p90 ошибки, с прогревом | p90 ошибки, без прогрева | Доля запросов с ошибкой <= 10%, с прогревом |
|---|---|---|---|---|
| 1 | 2.9% | 50.0% | 97.1% | 74% |
| 3 | 2.3% | 11.1% | 50.0% | 87% |
| 5 | 1.2% | 4.7% | 6.3% | 90% |
| 7 | 0.7% | 3.7% | 4.4% | 94% |

Разброс по диапазонам времени ([repeatability_by_time_bin.csv](../reports/stage1/repeatability_by_time_bin.csv)):

| Диапазон t(q) | Запросов | Медиана CV | Медиана отношения "первый запуск / эталон" | Максимум этого отношения |
|---|---|---|---|---|
| < 1 мс | 3 | 0.70 | 7.0 | 12.0 |
| 10-100 мс | 3 | 0.03 | 1.19 | 1.53 |
| 0.1-1 с | 17 | 0.02 | 1.08 | 1.97 |
| > 1 с | 8 | 0.04 | 1.04 | 1.12 |

Выводы:

1. **Прогрев обязателен.** Первый запуск у 26% запросов медленнее эталона более чем на 20%. В диапазоне 0.1-1 с он бывает почти вдвое медленнее: TPC-H Q3 - 1151 мс против 584 мс, генераторный `orders_group_by` - 606 мс против 314 мс. Без прогрева p90 ошибки при k = 3 составляет 50%. Обычно одного прогревочного запуска достаточно: ошибка второго запуска (k = 1 с прогревом) по медиане уже 2.9%. Исключения бывают: при сборе датасета у Q3 после прогрева медленными остались ещё два запуска (этап 3), но медиана из пяти это выдерживает.
2. **K = 5 достаточно.** С прогревом ошибка медианы <= 4.7% для 90% запросов. Переход к K = 7 улучшает p90 только до 3.7%, но увеличивает время сбора на треть: 8 запусков вместо 6 с учётом прогрева. Принято W = 1, K = 5.
3. **Запросы короче 0.1 мс измеряются на пределе разрешения.** У трёх генераторных шаблонов (точечный поиск по ключу, фильтр с LIMIT, JOIN с LIMIT) t ~ 0.01-0.02 мс, а `Execution Time` выводится с точностью 0.001 мс. Относительный разброс здесь велик (CV от 0.22 до 0.74, медиана 0.70), хотя абсолютный составляет сотые доли миллисекунды. Для регрессии на шкале `log(1 + t)` эта разница несущественна. Для метрик ранжирования это важно: порядок таких запросов между собой определяется шумом. Решение для этапа 5: дополнительно считать pairwise accuracy только по парам, у которых t различается больше уровня шума измерений.
4. **Тяжёлые запросы стабильны.** Для t > 10 мс медиана CV составляет 2-4%. Единичные выбросы до CV ~ 0.15 (Q3, Q9) медиана поглощает.
5. **Между сессиями измерений абсолютное время сдвигается сильнее, чем внутри сессии.** Те же 28 запросов с t >= 1 мс были повторно измерены при полном сборе датасета (этап 3), в отдельной, более поздней сессии. В медиане t(q) выросло на 6%, у 10% запросов - больше чем на 19%, максимум на 28% (Q11). При этом порядок запросов почти не изменился: Spearman между сессиями 0.993. Вероятная причина - изменившееся состояние хоста (Docker/WSL2, фоновые процессы Windows): БД и настройки в обеих сессиях одинаковы, что подтверждает отпечаток статистики.
