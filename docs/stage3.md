# Этап 3. Воспроизводимый стенд и корпус запросов

## 1. Стенд

Скрипт `python -m src.db.snapshot_environment` записывает параметры стенда и отпечаток выбранных полей `pg_stats` до и после серии. Совпадение отпечатков одной версии означает, что при снятии двух снимков значения проверенных полей совпали. Неизменность содержимого таблиц в течение серии принята как условие эксперимента. Хеш содержимого таблиц не рассчитывался.

| Компонент | Значение |
|---|---|
| СУБД | PostgreSQL 16.4 (`postgres:16.4`, Debian), `docker-compose.yml` |
| Хост | Windows 11, Docker Desktop (WSL2), 12 логических CPU, 7.9 ГБ ОЗУ для Docker |
| Данные | TPC-H, `dbgen -s 1` (SF = 1, генератор детерминирован), electrum/tpch-dbgen @ `32f1c1b` |
| Объём | lineitem 6 001 215 строк, orders 1 500 000, partsupp 800 000, part 200 000, customer 150 000, supplier 10 000; на диске с индексами 1562 МиБ ~ 1.53 ГиБ |
| Схема и индексы | `src/db/create_tpch_schema.sql`: первичные ключи + 9 индексов по внешним ключам, всего 17 индексов |
| Статистика | `ANALYZE` после импорта, `default_statistics_target = 100`; отпечаток `pg_stats` (sha256) в снимке |
| Конфигурация сервера | `shared_buffers = 1GB`, `jit = off`, `max_parallel_workers_per_gather = 0`; остальные параметры планировщика по умолчанию (`random_page_cost = 4`, `work_mem = 4MB` и т. д.) |
| Параметры сессии | `jit = off`, `max_parallel_workers_per_gather = 0`, `statement_timeout = 120 s` (дублируются в сессии, чтобы протокол работал и вне Docker) |

**Почему отключены JIT и параллелизм.** На стенде отключены JIT-компиляция и параллельное выполнение. Это фиксирует два условия эксперимента. Время выполнения по-прежнему зависит от загрузки хоста и состояния кэша. Перенос на конфигурацию с параллелизмом - отдельный эксперимент (8-й семестр).

**Контроль повторной сборки.** Фиксированные seed и версия генератора задают тексты запросов и данные TPC-H. После нового `ANALYZE` статистика может измениться из-за случайной выборки строк. Планы и Total Cost проверяются по новому `EXPLAIN`, показатели времени и выводы о ранжировании - по новым измерениям.

## 2. Корпус запросов

Корпус сохраняется в `data/queries/combined_tpch_queries.json`. Три команды для его сборки приведены в [README](../README.md#полное-воспроизведение-на-стенде). У каждого запроса есть `template_id` - идентификатор шаблона. Экземпляры одного шаблона отличаются только параметрами.

| Источник | Шаблонов | Запросов | Как получены |
|---|---|---|---|
| Собственный генератор (`src/db/generate_query_workload.py`) | 9 | 168 | перебор параметров: ключи, даты, сегменты, LIMIT |
| TPC-H qgen (`scripts/generate_tpch_queries.sh`) | 22 | 106 | 22 стандартных запроса x 5 seed (101, 202, 303, 404, 505) = 110, минус 4 повтора |
| Итого | 31 | 274 | |

Изменения по сравнению с 6 семестром:

- стандартные запросы TPC-H генерируются с фиксированными seed в 5 экземплярах (было по одному с неизвестным seed), поэтому у каждого шаблона TPC-H есть варианты для разбиения по шаблонам;
- Q15 больше не пропускается: `CREATE VIEW ... ; SELECT ...; DROP VIEW` переписывается в эквивалентный запрос с `WITH` (`convert_view_to_cte`);
- повторяющиеся тексты удаляются (`remove_duplicates`). У Q15 и Q18 мало возможных значений параметров, и разные seed дают одинаковые запросы: у Q15 из 5 вариантов уникальны 2, у Q18 - 4. Без удаления один и тот же запрос при случайном разбиении мог бы попасть и в train, и в test;
- добавлены поля `template_id` (шаблон) и `source` - источник запроса: `generator` или `tpch_qgen`. По `source` метрики считаются отдельно для двух частей корпуса (этап 2).

### Полученный датасет

Сбор по протоколу этапа 1 (1 прогрев + 5 замеров) занимает около 20 минут. Все 274 запроса выполнены без таймаутов. В опубликованной серии совпал отпечаток семи полей статистики до и после сбора (`df3c96b8...`, [environment.json](../reports/stage3/environment.json) и [environment_after_collection.json](../reports/stage3/environment_after_collection.json)).

В опубликованных снимках версия явно не записана (исходный формат, v1). Для схемы `public` учитывались `tablename`, `attname`, `null_frac`, `avg_width`, `n_distinct`, `most_common_vals` и `histogram_bounds`. Для этой серии нельзя ретроспективно проверить частоты частых значений или корреляцию по сохранённым хешам.

В новых снимках (v2) добавлены `most_common_freqs` (частоты наиболее частых значений), `correlation` (связь порядка значений с физическим порядком строк) и `inherited` (учёт дочерних таблиц). Раздел `statistics` хранит версию расчёта, схему, список полей и SHA-256. Хеши можно сравнивать только при совпадении версии расчёта, схемы и набора полей.

| Диапазон t(q) | Запросов |
|---|---|
| < 1 мс | 100 |
| 1-10 мс | 5 |
| 10-100 мс | 12 |
| 0.1-1 с | 97 |
| >= 1 с | 60 |

- t(q): медиана 252 мс, 75-й процентиль 873 мс (описательная метка опубликованного CSV, 69 "тяжёлых" запросов), максимум 4.8 с (TPC-H Q1).
- Медиана CV по 5 замерам: 0.066. Флаг `is_unstable` (CV > 0.2) стоит у 84 запросов, 82 из них короче 1 мс, где сказывается разрешение таймера (этап 1). Ещё два случая:
  - `q0100` (1.02 мс) - на границе того же диапазона;
  - `tpch_s101_q03`: после прогрева первые два измеренных запуска ещё медленные - 1052 / 735 / 614 / 615 / 615 мс. Медиана 615 мс совпадает со стабильными запусками. По этим замерам нельзя определить долю данных в кэше.

## 3. Состав датасета и исключение фактических метрик

`python -m src.db.collect_dataset --label-quantile 0.75` формирует три файла:

| Файл | Содержимое |
|---|---|
| `data/processed/query_dataset.csv` | одна строка на запрос: служебные поля, признаки, t(q) и статистика повторов, бинарная метка |
| `data/processed/measurements.csv` | все запуски: `query_id`, номер запуска, признак прогрева, Execution Time, Planning Time |
| `data/processed/plans.jsonl` | для каждого запроса план `EXPLAIN` (источник признаков) и первый измеренный план `EXPLAIN ANALYZE` |

**Полнота серии.** Сборщик записывает по одному результату и одной записи в plans.jsonl на каждый выбранный query_id. При сбое он сохраняет статус timeout или error, причину и завершённые повторы, включая прогрев. Поле measured_runs учитывает только измеренные повторы. Если план ещё не получен, соответствующее поле JSON равно null. Отсутствующее или некорректное Execution Time делает попытку неуспешной. У неполной серии время запроса и бинарная метка остаются пустыми.

Перед сохранением сборщик сверяет результат с выбранным корпусом. Для проверки сохранённых файлов основной серии надо выполнить `python -m src.checks.check_collection`. В опубликованных данных проверены 274 запроса, 274 записи планов и 1644 повтора. Для проверки эксперимента этапа 1 та же команда принимает пути к его файлам и параметры серии.

```bash
python -m src.checks.check_collection --limit-per-template 1 --warmup-runs 0 --runs 15 \
  --dataset data/processed/repeatability/query_dataset.csv \
  --measurements data/processed/repeatability/measurements.csv \
  --plans data/processed/repeatability/plans.jsonl
```

В этой серии проверены 31 запрос и 465 повторов. Тесты ошибок сборщика запускаются командой `python -m unittest discover -s tests -p test_measurement_journal.py`.

Колонки разделены явно в `src/features/columns.py`:

- **служебные:** `query_id`, `template_id`, `source`, `query_type`, `expected_complexity`, `sql_text`, `status` и добавленное для новых серий поле `error`;
- **целевые и фактические (не признаки):** `execution_time_ms` (= t(q)), `exec_time_min/max/mean/std_ms`, `exec_time_cv`, `planning_time_ms`, `measured_runs`, `is_unstable`, `label`;
- **признаки:** 22 разрешённых поля из пяти групп. Перед обучением проверяется полный перечень колонок. Неизвестный столбец останавливает обучение с указанием имени.

Проверка `python -m src.checks.check_leakage`:

1. набор признаков в датасете совпадает с выходом `extract_sql_features` + `extract_plan_features`, лишних колонок нет;
2. в планах, из которых строятся признаки, нет полей, появляющихся только при ANALYZE (`Actual *`, `Execution Time`, буферы);
3. признаки, заново пересчитанные из сохранённого `EXPLAIN` и SQL-текста, совпадают с признаками в датасете для всех запросов.

Результат на собранном датасете:

```text
OK    Набор признаков совпадает с выходом экстракторов
OK    Планы для признаков получены без ANALYZE
OK    Признаки воспроизводятся из EXPLAIN и SQL-текста

Признаков: 22, запросов: 274
```
